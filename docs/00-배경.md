# 00 — 배경

## 한 줄

전 세계 국가가 참여한 반차별·인권 국제 조약과 그 서사를, **3D 인터랙티브 지구본**에서 탐색하고
**RAG 기반 AI**로 "이 나라는 왜/어떻게 참여하는가"를 공식 출처에 근거해 답변받는 풀스택 웹 플랫폼.

가칭 **Equalizer**. 원안은 `E-racism`(erase + racism). 범위를 차별 전반으로 넓히며 이름 재검토 중이고,
**이름은 완성 후에 정해도 프로젝트는 굴러간다.**

---

## 왜 만드는가

### 취업 (본질적 목적)
- **풀스택 증명**: 프론트(3D 인터랙션) + 백엔드(Spring, RAG 파이프라인, API) + DB(벡터 검색)를 하나로.
- **AI 통합 증명**: 단순 "LLM API 호출"이 아니라, RAG로 환각을 통제하고 공식 출처에 근거한 답변만 생성하는
  **데이터 거버넌스 설계**. 2026년 채용 시장에서 가장 수요가 높은 축.
- **3D 실무 경험 계승**: 회사에서 한 3D 시뮬레이션 경험을, 모델링 없이 웹으로 살리는 방향.
- **차별화**: 투두·쇼핑몰·SNS 클론이 아닌, 검증된 공식 데이터 + AI + 3D + 사회적 의미의 결합.

### 개인
- "차별을 지운다"는 원래 문제의식의 계승. 인종차별을 핵심 사례로 두되, 데이터 확보를 위해 차별 전반으로 확장.

## 무엇을 만드는가

| 기능 | 설명 | 우선순위 |
|---|---|---|
| **A. 3D 지구본** | 조약별 비준 현황으로 국가 색칠, 클릭 시 상세 | 코어 |
| **B. RAG 서사 응답** | 국가·조약 맥락 질의 → 공식 문서 근거 답변, 없으면 "자료 없음" | 코어 (차별화) |
| C. 2D 보조 시각화 | 조약별 비교, 연도별 비준 추이 | 후순위 |
| D. 참여형 학습(퀴즈) | 혐오표현 판단 퀴즈 등 | 후순위 |
| E. P2P 화상 토론 | WebRTC. **난이도 최상** | 취업 후 |

> ⚠️ **D·E를 A·B와 동시에 벌이면 완성이 무너진다.** 과거에 이 프로젝트 하나에
> 3D + WebRTC + i18n + CMS를 전부 넣으려다 "5개 프로젝트를 뭉친 것"이 되어 브레이크를 걸었다.
> 코어(A·B)를 **배포 가능한 상태로** 완성하는 것이 최우선.

## 설계의 중심 원칙

### 1. AI는 판단자가 아니라 설명자다
AI가 "이 나라는 차별이 심하다"고 판단하게 두지 않는다.
실재하는 공식 문서를 검색해 **그 범위 안에서만** 요약·설명한다.
근거가 없으면 답하지 않는다. 이건 프롬프트 부탁이 아니라 **아키텍처로 강제**한다.

### 2. "차별 지도"가 아니라 "조약 참여·이행 현황"이다
특정 국가를 낙인찍는 프레임을 쓰지 않는다. 긍정적·중립적 서술.
UN·UNESCO 공식 정의만 인용하고, 판단하지 않는다.

### 3. 자료가 없으면 없다고 말한다
데이터 공백을 숨기거나 추정으로 메우지 않는다.
**"자료 없음"은 결함이 아니라 이 프로젝트의 정체성이자 신뢰성의 증거다.**
그래서 빈 상태 화면을 가장 공들여 설계한다.

### 4. 출처는 원출처 + 경유처를 함께
"UNESCO가 인용했다" ≠ "UNESCO가 생산했다".
논쟁적 내용은 "국제적으로 논의 중" 중립 표기.

## 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 특정 국가 "차별국" 낙인 | 조약 참여·이행 프레임, 긍정적 서술 |
| 정치적 민감성 | 공식 정의만 인용, 판단하지 않음, 발화 주체 명시 |
| AI 환각 | RAG로 근거 강제, 없으면 답변 거부 |
| 국가별 데이터 불균형 | 정직하게 "자료 없음" 표시 — 오히려 신뢰성의 증거 |
| **스코프 과잉 (완성 실패)** | **Phase 경계 엄수. 가장 큰 리스크.** |
| 콘텐츠가 코드보다 무거워짐 | "AI 판단자"가 아닌 "실재 데이터 설명자"로 재설계해 해소됨 |

## 작업 방식

### 학습 루프 (모든 작업 단위에 적용)
1. **짓기 전에 설명** — 무엇을 왜 만들 건지 먼저. 선택지가 둘이면 먼저 묻는다
2. **개발자가 입장을 정한다** — 틀려도 됨. 답을 보기 전에 입장이 있는 게 핵심
3. 코드 작성
4. **개발자가 3문장을 쓴다**
   - ① 이게 없으면 무엇이 깨지는가
   - ② 다른 선택지는 무엇이었고 왜 이걸 골랐는가
   - ③ 느려지면 어디부터 보는가
5. `docs/decisions/NNN-제목.md`에 기록
6. **3문장을 못 쓰면 그 작업은 끝나지 않은 것**

> 이 루프의 목적: AI가 짠 코드를 그대로 넘기면 **설명 못 하는 코드**가 쌓인다.
> 그건 그 기술을 안 쓴 것보다 나쁘다. 면접에서 "왜 이렇게 했어요?"에 막히는 순간
> 포트폴리오 전체의 신뢰가 깎인다.

### 위임 경계
**일회성 설정은 위임, 꼬리질문이 붙는 영역은 개발자 본인.**
면접은 Dockerfile을 파지 않는다. API 설계와 RAG를 판다.

| 영역 | AI가 해도 되는 것 | 개발자가 결정할 것 |
|---|---|---|
| 인프라 | Dockerfile, compose, CI, 마이그레이션 | 계정·대시보드·환경변수 |
| 데이터 | ETL 구현 | 범위·필터 결정, 매핑 검수 |
| 백엔드 | 보일러플레이트, 설정 | **API 설계, 응답 모양, 에러 정책** |
| RAG | 라이브러리 연결 | **청킹 단위, 필터 전략, 프롬프트, 실패 처리** |
| 프론트 | 컴포넌트 구현 | 상태 구조, 인터랙션 설계 |
| 문서 | 초안 | **`decisions/`의 3문장은 반드시 본인** |
