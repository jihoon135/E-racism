# 02 — 아키텍처

## 1. 기술 스택

| 레이어 | 기술 | 선택 근거 |
|---|---|---|
| 프론트 | React 19 + TypeScript + **Vite** | SEO 불필요한 단일 인터랙티브 앱 — Next.js의 SSR이 할 일이 없다 |
| 3D | `react-globe.gl` (ThreeJS/WebGL) | 무료, **3D 모델링 불필요** — 코드로 데이터만 바인딩 |
| 상태 | TanStack Query + Zustand | 서버상태/클라상태 분리. 채용공고 빈출 조합 |
| 백엔드 | **Spring Boot 4.x** + Spring Data JPA | 백엔드 공고 비중이 프론트의 약 1.7배. React/Next는 이미 보유 |
| AI | **Spring AI** (RAG Advisor + PgVectorStore) | Java 단일 백엔드 유지 — Python 서비스를 따로 두면 배포가 2개 |
| DB | PostgreSQL + **pgvector** (Supabase) | 일반 테이블 + 벡터를 한 DB에서. 별도 벡터DB 불필요 |
| 계약 | springdoc-openapi → openapi-typescript | DTO 변경이 프론트 빌드를 깨뜨린다 |
| 로컬 | docker-compose (postgres + pgvector) | 한 줄 기동 |
| 배포 | Vercel(web) + Railway/Fly/Render(api) + Supabase(db) | 무료 티어 |

### 왜 Next.js가 아닌가
로그인 없는 단일 인터랙티브 앱에 SSR이 할 일이 없다. "Next 써봤다"는 이미 이력에 있다.
Vite로 가면 번들·라우팅을 직접 보게 되고, 그게 "판단할 수 있는 깊이"의 재료가 된다.

### 왜 별도 벡터DB를 안 쓰는가 (면접 빈출)
> "이 규모에는 pgvector로 충분하고, DB를 하나로 유지해 운영 복잡도를 낮췄습니다.
> 데이터가 수백만 건으로 커지면 전용 벡터DB를 검토하는 게 맞다고 봅니다."

## 2. 레포 구조 — 단일 레포, 모노레포 툴링 없음

```
equalizer/
├── apps/
│   ├── web/                 React + TS + Vite
│   └── api/                 Spring Boot (Gradle)
├── packages/
│   └── api-types/           OpenAPI에서 생성된 TS 타입 (자동 생성물)
├── data/
│   ├── raw/                 내려받은 원본 (gitignore, 체크섬만 커밋)
│   └── seed/                정규화된 시드 (커밋)
│       ├── ratifications_6treaties.csv
│       └── country-alias.json
├── scripts/                 ETL 파이프라인
├── docs/                    이 문서들
│   └── decisions/           설계 결정 로그
├── docker-compose.yml
└── README.md
```

### 왜 하나의 레포인가
- **Claude Code가 작업 디렉터리 하나에서 돈다.** 레포를 나누면 컨텍스트가 쪼개져
  "API 응답 필드 바꾸고 프론트도 같이 고쳐줘"가 한 턴에 안 된다. 1인 + AI 페어 환경에서 이 비용이 가장 크다.
- **API 계약이 계속 바뀌는 단계**다. 프론트/백 변경을 하나의 커밋으로 묶어야
  "이 커밋이 왜 양쪽을 건드렸는지"가 히스토리에 남는다.
- 배포는 어차피 갈라진다. Vercel은 Root Directory로 `apps/web`만 빌드하고,
  백엔드 호스트는 같은 레포에서 `apps/api`를 본다.

### 왜 Nx·Turborepo를 안 쓰는가
**JS 생태계 전용 태스크 그래프 도구**라 Gradle과 섞으면 설정 복잡도만 늘고 1인 프로젝트에서 얻는 게 없다.
필요한 건 툴링이 아니라 한 레포 안의 두 폴더다.

### 면접 답변 (이건 반드시 물어본다)
> "1인 개발이고 프론트–백 API 계약이 자주 바뀌는 단계라, 계약 변경을 원자적 커밋으로 묶으려고
> 단일 레포로 갔습니다. 대신 Nx 같은 모노레포 툴링은 안 썼는데, Java와 JS가 섞여 있어
> 태스크 그래프의 이득이 없고 설정 복잡도만 늘기 때문입니다.
> 팀이 나뉘고 배포 주기가 달라지면 분리하는 게 맞다고 봅니다."

**트레이드오프를 말할 수 있으면 어느 쪽을 골랐든 통과한다. "요즘 모노레포가 트렌드라서"는 최악의 답이다.**

### 타입 안전성
`springdoc-openapi`로 OpenAPI 스펙을 뽑고 → `openapi-typescript`로 프론트 타입 생성.
백엔드 DTO를 바꾸면 **프론트 빌드가 깨진다** = 계약 위반이 컴파일 타임에 잡힌다.
단일 레포라 한 커맨드로 돌릴 수 있고, **이것이 단일 레포를 고른 가장 강한 기술적 근거**다. README에 명시할 것.

## 3. 데이터 흐름

```
OHCHR 전량 export  ──(1회 다운로드)──▶  ETL  ──▶  PostgreSQL + pgvector
                                                        │
                                          Spring Boot API ─┘
                                                        │
                                                  React 프론트
```

**사용자 요청 시 OHCHR을 호출하는 일은 없다.** 우리 DB만 본다.

### 무거운 건 미리, 가벼운 건 그때
가공(ISO3 매핑·필터·임베딩)은 **배치**로 미리 끝낸다. API는 정리된 걸 꺼내기만 한다.
요청 시점에 가공하면 응답이 수 초씩 걸린다.

> 면접 "성능은 어떻게 챙겼나" → **애초에 요청 경로에서 무거운 일을 빼는 것**이
> 캐싱·인덱스보다 먼저 나와야 할 답이다.

### ETL 6단계 (`scripts/`)
```
1. fetch      원본 다운로드 → data/raw/ (체크섬 기록, gitignore)
2. normalize  국가명 → ISO3 매핑, 실패 건 로그
3. filter     범위 적용
4. chunk      권고 1건 = 1청크          ← Phase 5
5. embed      임베딩 API, 배치 + 재시도   ← Phase 5
6. load       pgvector upsert
```

**멱등(idempotent)하게 만들 것.** 두 번 돌려도 중복 적재가 안 되게 — insert가 아니라 upsert.
안 그러면 시드를 다시 돌릴 때마다 DB를 비워야 한다.

> "ETL 파이프라인을 직접 설계하고 멱등성을 보장했다"는 백엔드 서사가 포트폴리오에 거의 없다.
> README에 이 6단계 다이어그램을 넣을 것.

## 4. DB 스키마

### Phase 1~4에서 만드는 것 (3개)

```sql
country (
  iso3        CHAR(3) PRIMARY KEY,
  name_en     TEXT NOT NULL,
  name_ko     TEXT,
  region      TEXT
);

treaty (
  code             TEXT PRIMARY KEY,      -- ICERD, CEDAW, CRPD, CRC, ICRMW, ICCPR
  name_en          TEXT NOT NULL,
  name_ko          TEXT,
  adopted_year     INT,
  data_updated_at  DATE                   -- 조약별 원본 갱신일 ← UI 표시용
);

ratification (
  iso3                            CHAR(3) REFERENCES country(iso3),
  treaty_code                     TEXT    REFERENCES treaty(code),
  status                          TEXT NOT NULL,  -- STATE_PARTY | SIGNATORY | NO_ACTION
  date_signature                  DATE,
  date_ratification               DATE,
  date_individual_communications  DATE,   -- 개인 진정 가능 여부
  date_inquiry_procedure          DATE,   -- CEDAW/CRC/CRPD만 존재
  PRIMARY KEY (iso3, treaty_code)
);
```

**📌 `date_individual_communications`를 따로 두는 이유**
ICERD는 182개국이 비준했지만 개인 진정은 59개국만 수락했다. ICRMW는 60개국 중 4개국.
**"가입했다"와 "개인이 실제로 구제받을 수 있다"는 다르다.**
이 두 층을 구분해 보여주는 것이 단순 비준 지도와 갈리는 지점이다.

**📌 `status`는 유도값**이다. 원본에 없고 날짜에서 계산한다(`01-데이터.md` §2-1).
ETL에서 한 번 계산해 저장한다 — 조회할 때마다 계산하지 않는다.

### Phase 5에서 추가 (그 전에 만들지 않는다)

```sql
document (
  id          BIGSERIAL PRIMARY KEY,
  iso3        CHAR(3) REFERENCES country(iso3),
  mechanism   TEXT,        -- Treaty Bodies | UPR | Special Procedures
  body        TEXT,        -- CERD, CEDAW 위원회 등
  theme       TEXT[],      -- ML 자동 분류 — 필터용, 표시용 아님
  year        INT,
  source_url  TEXT NOT NULL,
  text        TEXT NOT NULL
);

document_embedding (
  doc_id     BIGINT REFERENCES document(id),
  embedding  vector(1536)
);
-- HNSW 인덱스
```

`document.theme[]` · `iso3` · `year`가 RAG 메타데이터 필터의 입력이다.

> 빈 테이블을 미리 만들면 그걸 바라보며 RAG를 생각하게 되고 집중이 흐려진다. Phase 5에 만든다.

## 5. API 설계 원칙

- 지구본은 **198개국을 한 번에** 받는다. 응답에 불필요한 필드를 실으면 그만큼 전부 곱해진다.
- 목록 응답과 상세 응답을 분리한다.
- 에러는 HTTP 상태 + 구조화된 바디. "자료 없음"은 **에러가 아니라 정상 응답**이다.

```
GET /api/treaties                               조약 목록 + 각 조약 기준일
GET /api/treaties/{code}/ratifications          지구본 색칠용 (경량)
GET /api/countries/{iso3}                       국가 상세 — 6개 조약 전체 상태
POST /api/ask                                   RAG 질의          ← Phase 5
```

## 6. 환경 분리

| | 로컬 | 배포 |
|---|---|---|
| DB | docker-compose postgres | Supabase |
| API | localhost:8080 | 백엔드 호스트 |
| Web | Vite dev server | Vercel |

- `.env`는 커밋하지 않는다. `.env.example`만 커밋한다.
- **CORS는 Phase 2에서 반드시 한 번 막힌다. 정상이다.**
- 무료 플랜은 유휴 시 컨테이너를 재운다. 첫 요청에 JVM 부팅까지 겹치면 수십 초.
  **포폴 링크를 누른 면접관이 로딩만 보다 나가는 상황**이라 실제 문제다 → Phase 6에서 대응.
